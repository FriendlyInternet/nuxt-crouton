IMPLEMENT this ONE leaf issue end-to-end. Do NOT decompose it, do NOT create sub-issues, do NOT spawn subagents — it is already a leaf. Read issue #{{issue}} (gh issue view {{issue}}), then {{branch_instr}}. For a scaffold/generate task, RUN the crouton generator (e.g. crouton config / generate_collection) — its output IS committed for you, so do NOT hand-write generated files. Author only the inputs (schema, config) with the edit/write tools (never shell redirects or heredocs) so they are captured. Run the touched app typecheck ONCE to sanity-check (pnpm --filter <app> typecheck), but do NOT loop trying to make typecheck fully green — a harness acceptance gate typechecks the result and reports failures, so stop after your change plus one check instead of grinding on it. Do NOT run git commit and do NOT open a pull request — the workflow commits your inputs AND the generator output and opens the PR, so you never need to. If you are genuinely blocked, or must hold for any gate or question, do NOT guess and do NOT post it yourself: write it with the write tool to {{question_file}} — line 1: the one decision + your recommendation; line 2: `**Needs:** answer|action|approval`; then the options and what a fresh session must not lose (depth inside `<details>`) — and end the run. The step after you posts it on the issue, adds status:blocked and ties it to your PR, so the owner's answer comes back to you. Making no file changes and no hold is a FAILED run.

SHARED UI PIECES NEED NO PREVIEW PAGE (#2462) — a change to a `.vue` under `packages/*/app/components` gets a live review link automatically: the gallery (`pocs/gallery`) deploys for your PR and comments one link per changed piece. Do NOT hand-write a preview page in a POC. If the piece needs input to look like itself, add one line for it in `pocs/gallery/app/review-samples.ts`.

REPRODUCE BEFORE YOU FIX (#2513) — when the issue says "reproduce" (or is a UI bug at a screen size), boot the app yourself: `pnpm preview <app> --no-login` is not enough, use `pnpm preview <app>` (seeds + mints the review login, prints the sign-in URL), then drive it with Playwright using a device descriptor (`hasTouch` for touch bugs). Paste the before/after observation into your issue comment. "I did not boot the app" is a failed step, not a caveat.

STAGING BUGS (#2760) — a bug reported on staging (an app URL on `*.pmcp.dev`) is reproduced FIRST with `node scripts/staging-get.mjs <app> <path>` (signs in as the review login; `<team>` in the path is filled with its active team id). To reproduce a failing save, send it: `--method PATCH --body '<json>'` (or `--body-file`), using the exact body the app sends (read it from the component/composable code). Staging only (`*.pmcp.dev`; production is refused). Prefer throwaway records and delete them after. Put the HTTP statuses and row counts in your archaeology comment. "Can't reach staging" is not an acceptable finding.

REUSE BEFORE YOU WRITE — before adding a helper, composable or util, search for one: `grep -rniE '<verb|noun>' packages/*/app/utils packages/*/app/composables packages/*/server/utils` (plain grep; `rg` is not installed on the runner). Reuse what you find, or name the closest one in your issue comment and say why it does not fit.

DOCS TRAVEL WITH THE CODE — a new component, composable, endpoint or generator feature updates the file the root `CLAUDE.md` "Maintaining AI Documentation" table names, in the same change.

DOC MENTIONS (#4052) — after editing, run `node scripts/doc-mentions.mjs --base HEAD`. Each line it lists is a package CLAUDE.md line that still uses a component, composable or config key your edits removed or renamed. Edit that line in the same change (the new name, or drop the sentence if the thing is gone), or leave it and give a reason. Leave lines in a package this ticket does not approve (the packages notice tells you), and mark them `Debt: package not approved`. Post one top-level issue comment (`gh issue comment {{issue}}`), even when nothing is listed: after the provenance header, a line `<!-- doc-mentions -->`, then one line per listed line, `<file>:<line> — fixed` or `<file>:<line> — Debt: <why>`. When it prints `doc-mentions: none`, write `Doc mentions: none`. When it stops with exit 2, write `Doc mentions: could not run — <its message>`. Post this comment only in a run where you edited files; when you changed no file, or you stop blocked, post none.

LOGIC LIVES IN scripts/, NOT IN WORKFLOWS (#3452) — a decision (if/else, parsing, matching) goes in a scripts/*.mjs with a node:test file next to it; the workflow step only calls it. A new or grown run:/script: block over 40 lines fails CI (scripts/workflow-inline-size.mjs).

UNRELATED PROBLEMS GO IN A TICKET (#3249) — a problem you find that this issue did not ask about (an old type error, a broken page elsewhere) does NOT go into this PR's diff: search open issues first (gh issue list --search …); comment on a match, otherwise open a new type:fix ticket with the app's scope label and link it in your issue comment.

THE STEP LIST IS WRONG (#3846) — if this ticket is one step of a rolling epic (`step=` in its pipeline block) and building it shows the epic's step list itself is wrong (a missing step, a wrong order), post a top-level comment on the EPIC that contains `<!-- epic-plan-wrong -->` and opens with `## 🔀 Blocked — the step list is wrong: <one line>`, then add `status:blocked` to this issue and stop.
