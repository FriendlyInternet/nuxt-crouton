## A collection

A **collection** is one kind of record — products, orders, posts. It is one database table plus the screen, API and types around it. You describe it with a field file and list it in `crouton.config.js`:

```js [crouton.config.js]
export default {
  collections: [
    { name: 'products', fieldsFile: './schemas/products.json' },
    { name: 'orders', fieldsFile: './schemas/orders.json' }
  ],
  targets: [
    { layer: 'shop', collections: ['products', 'orders'] }
  ],
  dialect: 'sqlite'
}
```

Use a plural name (`products`, not `product`). The generator derives the singular itself, for example for the route parameter `[productId]`.

Every collection also gets these columns, so you never list them in the field file: `id`, `teamId`, `owner`, `createdAt`, `updatedAt`, `createdBy`, `updatedBy`. The field file format is on [Schema format](/generation/schema-format).

## A layer

A **layer** is a folder under `layers/` that is also a [Nuxt layer](https://nuxt.com/docs/getting-started/layers). `targets` decides which layer each collection goes into. One layer holds many collections, so group them by area of the business:

```
layers/
├── shop/
│   ├── nuxt.config.ts
│   └── collections/
│       ├── products/
│       └── orders/
└── blog/
    ├── nuxt.config.ts
    └── collections/
        ├── posts/
        └── authors/
```

The generator adds each layer to `extends` in your app's `nuxt.config.ts`. You don't wire layers by hand. A small app can use a single layer.

## The names one collection gets

The layer name is part of every name. That way `shop/products` and `catalog/products` can exist in one app without clashing. For layer `shop` and collection `products`:

| What | Name |
| --- | --- |
| Collection key (used everywhere in code) | `shopProducts` |
| Form component | `ShopProductsForm` (file `_Form.vue`) |
| List component | `ShopProductsList` (file `List.vue`) |
| Composable | `useShopProducts` |
| Config object | `shopProductsConfig` |
| API path | `/api/teams/[id]/shop-products` |
| Database table | `shop_products` |
| Admin screen | `/admin/<team>/crouton/shopProducts` |

## The registry

The generator registers each collection in your app's `app/app.config.ts`, under its key:

```ts [app/app.config.ts]
import { shopProductsConfig } from '../layers/shop/collections/products/app/composables/useShopProducts'

export default defineAppConfig({
  croutonCollections: {
    shopProducts: shopProductsConfig
  }
})
```

Every core helper that takes a collection name looks it up here. That includes `useCollectionQuery`, `useCollectionMutation`, `useCrouton().open` and `<CroutonCollection collection="…">`. So the name you pass is always the **key** (`shopProducts`). The layer folder name, the API path and the table name don't work there. A name that isn't registered throws `Collection "…" not registered`.

The config object holds the collection's API path, default values, columns and field list. It can also hold a few settings that core reads, for example `container: 'modal'` to open the form in a modal instead of the default slide-over (see [Data operations](/fundamentals/data-operations#opening-the-form)).

## Every row belongs to a team

Each record carries a `teamId`. The generated API routes live under `/api/teams/[id]/…`, and each one checks that the signed-in user is a member of that team before it touches the database. A query only returns the current team's rows, and a new record is stamped with that team. How users, teams and roles work: [Team-based auth](/advanced/team-based-auth).
