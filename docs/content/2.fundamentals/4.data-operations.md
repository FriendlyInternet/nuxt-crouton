All of these take the collection **key** from `croutonCollections` (`shopProducts`), and all of them call the collection's generated API routes for the current team. The full signatures are in [Composables](/api-reference/composables).

## Reading a list

```vue
<script setup lang="ts">
const { items, pending, error, refresh } = await useCollectionQuery('shopProducts')
</script>

<template>
  <p v-if="error">Could not load products.</p>
  <ul v-else>
    <li v-for="product in items" :key="product.id">{{ product.name }}</li>
  </ul>
</template>
```

`items` is always an array: empty while loading, empty when there is no team yet, and typed from the collection's `types.ts`. `data` is the raw response.

### Passing query parameters

Pass `query` as a `computed` (or a `ref`). The query refetches whenever its value changes. Pass `watch: false` to refetch only when you call `refresh()`.

```ts
const categoryId = ref<string>()

const { items } = await useCollectionQuery('shopProducts', {
  query: computed(() => ({ categoryId: categoryId.value }))
})
```

Parameters are sent as the URL query string to the generated `index.get.ts`. Out of the box, that route understands only these:

| Parameter | Effect |
| --- | --- |
| `ids=a,b,c` | only those records |
| `page`, `pageSize` | one page, returned as `{ items, total, page, pageSize }` (`pageSize` is capped at 100) |
| a reference field, e.g. `categoryId=…` | only records pointing at that record (every field with a `refTarget`) |
| `owner`, `createdBy`, `updatedBy` | only records owned, created or last changed by that user |

**Anything else is ignored.** `search`, `sortBy` or `status` return the full list unchanged, with no error. To filter on another field, either filter `items` in a `computed` (fine for small collections), or add the parameter to the collection's `index.get.ts` and `getAllShopProducts` in `server/database/queries.ts`. Those are your files.

### Pages

Turn on pagination and the composable manages the page for you:

```vue
<script setup lang="ts">
const { items, page, pageCount, nextPage, prevPage } = await useCollectionQuery('shopProducts', {
  pagination: { pageSize: 20 }
})
</script>

<template>
  <ul>
    <li v-for="product in items" :key="product.id">{{ product.name }}</li>
  </ul>
  <UButton :disabled="page === 1" @click="prevPage">Previous</UButton>
  {{ page }} / {{ pageCount }}
  <UButton :disabled="page === pageCount" @click="nextPage">Next</UButton>
</template>
```

It also returns `pageSize` (writable; changing it goes back to page 1), `total`, `setPage(n)` and `paginationData`. Without `pagination`, `page` and friends exist but do nothing, and the route returns every row.

### One record

```ts
const route = useRoute()
const { item, pending } = await useCollectionItem('shopProducts', () => String(route.params.id))
```

`item` is the record or `null`. The id can be a string, a `ref` or a getter. A getter or `ref` refetches when it changes.

## Saving and deleting

```ts
const { create, update, deleteItems } = useCollectionMutation('shopProducts')

const product = await create({ name: 'Widget', price: 19.99, inStock: true })
await update(product.id, { price: 24.99 })   // only the fields you send change
await deleteItems([product.id])
```

- The server fills in `id`, `teamId`, `owner`, `createdBy` and `updatedBy` on create, and `updatedBy` / `updatedAt` on update. Don't send them.
- The body is validated against the collection's Zod schema. Unknown keys are dropped.
- **On failure** an error toast is shown and the call throws, so wrap it in `try` / `catch` if you need to react. There is no success toast; show your own if you want one.
- `isReady` is `false` until the team is known. Calling `create` before that throws `Team context not yet available`.

For a one-off call without setting up the composable, `useCroutonMutate` does the same thing:

```ts
const { mutate } = useCroutonMutate()
await mutate('create', 'shopProducts', { name: 'Widget' })
await mutate('update', 'shopProducts', { id: 'abc', price: 9 })   // update needs data.id
await mutate('delete', 'shopProducts', ['abc'])
```

### Who may change what

By default, every team member can list and create records. A member can **update or delete only records they own**. Team admins and owners can change any record in the team. For someone else's record, the route answers `404 … not found or unauthorized`.

::callout{icon="i-lucide-triangle-alert" color="amber"}
`deleteItems` treats a 404 as "already gone" and does not report it. So when a member deletes a record they don't own, the call succeeds, nothing is deleted, and the row is still there after the list refreshes.
::

To tighten this per collection, set `access` on its entry in `crouton.config.js` and regenerate: `create: 'admin'` (only admins and owners may create), `list: 'own'` (members see only their own rows).

## Opening the form

`useCrouton()` opens the generated form in a container. The app shell already mounts it.

```ts
const { open, close, closeAll } = useCrouton()

open('create', 'shopProducts')                                // empty form
open('create', 'shopProducts', [], 'slideover', { inStock: false })  // with starting values
open('update', 'shopProducts', [product.id])                  // fetches the record, then shows it
open('delete', 'shopProducts', [a.id, b.id], 'dialog')        // core's delete confirmation
```

The arguments are: action, collection key, record ids, container, starting values (create only).

- **Containers:** `slideover` (default), `modal`, `dialog` or `inline`. `<CroutonTableHeader>`'s create button uses the collection's `container` setting from its config object, or `slideover` if none is set.
- **`update` and `view`** fetch the record first. If that fails, an error toast is shown and nothing opens. `view` uses a `ShopProductsDetail` component when your app has one, else core's generic detail view.
- **`delete`** never uses your `_Form.vue`. It shows core's confirmation for the given ids.
- **Stacking:** opening a form from inside a form stacks a new one on top, for example to add a missing category while editing a product. Up to 5 can be open; a 6th shows a warning and doesn't open.
- `close()` closes the top one and `closeAll()` closes all of them. `showCrouton` is `true` while any is open.

## Caching and refresh

Each `useCollectionQuery` call is cached under the key `collection:<key>:<query as JSON>`, for example `collection:shopProducts:{"categoryId":"c1"}`. Two components with the same query share one request.

After every `create`, `update` and `deleteItems`, core refreshes **every** cached query for that collection, whatever its parameters, so all lists on the page update. It also refreshes the single-record caches of the ids involved (`collection-item:<key>:<team>:<id>`, used by `useCollectionItem`; each id and team has its own cache). If the collection's config declares `references`, it refreshes the referenced records too.

Data changed outside these composables (a direct `$fetch`, another tab) is not noticed. Call `refresh()`, or refresh all queries of a collection the way core does. `refreshNuxtData` takes keys, not a filter function:

```ts
const keys = Object.keys(useNuxtApp().payload.data)
  .filter(key => key.startsWith('collection:shopProducts:'))
await refreshNuxtData(keys)
```

With `@fyit/crouton-collab` installed, a list also refetches when another user changes the same collection.
